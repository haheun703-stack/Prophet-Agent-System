## §2. 오늘의 개선 — [F-29] 아침 점검 무인화 (자동화 코드 적용)

### 문제
저녁 20:10 데이터 요약은 cron 자동인데 **아침 점검만 사람(세션) 의존**이었다.
7/29 세션 미개설로 A1~A9가 하루 통째 공백이 된 것이 실증. 오늘 아침에도 단타봇이
**SSH 8회**를 수동으로 돌려 위 표를 만들었다 — 세션이 안 열리면 그 8회는 아무도 안 돈다.

### 처방 (신설 `tools/daily_ops_check.py` · 평일 **08:30 cron** · 텔레그램 1건)
read-only 관측기. A1~A6·A9를 자동 판정해 사장님께 1건 발송.
A7(노트북 미러)·A8(업무일지)은 VPS에서 관측 불가/사람 몫이라 대상 외.

설계 요점 — 과거 사고를 코드로 되갚은 것들:

1. **기준 거래일 앵커** — "로그의 마지막 블록"이 아니라 *ref(직전 거래일) 블록*을 찾는다.
   마지막 블록으로 짜면 **휴장일 다음 거래일마다 정상을 FAIL로 오탐**한다(A2·A3·A4 공통).
   점검기가 늑대소년이 되면 존재 이유가 사라진다.
2. **SKIP→WARN 승격 + 초록불에 "점검 불가 N건" 병기** — 운영기(VPS)에서 로그 부재는
   '정상 스킵'이 아니다. 이게 없으면 로그가 통째로 사라진 날 전 항목 SKIP → "이상 없음"이
   발송된다([F-22] 조용한 사망과 정확히 같은 통로).
3. **판정 수치 위임** — 스코어보드/데드라인은 `strategy_deadline_check.build_report()`를
   호출한다. 클론을 뜨면 [F-37](CAP_VIEW_N 로컬 복제) 재발이다. 이를 위해 해당 파일의
   main() 로직을 함수로 분리(동작 무변경·⑲-4는 subprocess `--notify` 호출이라 무영향).
4. **항목별 예외 격리 + exit 0** — 한 항목이 죽어도 나머지 점검과 발송은 산다(cron 무차단).
5. **[F-4] 동시 소진** — `notify_data_freshness.py`에 실행 스탬프
   `[notify] === YYYY-MM-DD HH:MM:SS 실행 (기준 <date>) ===` 추가. 이 로그엔 시각이 없어
   A3 확인이 tail 순서에 의존했다. 스탬프가 있어야 (1)이 성립한다.

### 검수 (4-Tier)
- **Tier 2** 호출 site: ⑲-4는 `[PY, "tools/strategy_deadline_check.py", "--notify"]` **subprocess** →
  리팩터 무영향 확인. `build_report` 이름 충돌 없음(다른 2곳은 시그니처·모듈 상이·top-level import 0).
  로그 로테이션 부재 확인(logrotate.d에 bodyhunter 항목 0·`.1/.gz` 0) → tail 한도 안전.
- **Tier 3 VPS 실증** — 양성/음성 대조 모두 수행. **음성 대조가 버그 2건을 잡았다**:
  - `last_trading_day(d)`가 **d를 포함하지 않는** 직전 거래일인데 `today-1일`을 넘겨 **이틀 전**이
    기준이 됐다 → A3가 매일 오탐할 뻔. (VPS 첫 실행에서 기준 7/29로 찍혀 발각)
  - 리팩터 잔재 `NameError: name 'day'` — 요약 라인 결손 경로에서만 터짐.
    **항목 격리 설계 덕에 전체 점검은 살아남았고**, 격리가 없었으면 조용히 전체가 죽었다.

## §3. [F-19] 규명 — 결론이 뒤집힘 + [F-46] 신설

7/30 장부에서 **cap5 −21.07%p인데 일일 CB는 −6%p**인 게 눈에 걸려 정량화했다.

**상한 5건 시퀀스 안에서 CB를 재적용해도 11 유효일 전부 무변화**
(51건 −69.67%p → 51건 −69.67%p · 차이 **0.00%p** · CB로 잘린 날 **0일**).

원인 실측:

| | 값 |
|---|---|
| 상한 5건 **진입** 소요(첫→막) | 중앙 **7분** (최소 0분·최대 25분) |
| **CB 발동** − 마지막 진입 | 중앙 **+30분** · **8/8일 전부 사후** |
| 7/30 실례 | 진입 09:26~09:31 완료 → CB 09:46:35 |

즉 **정합 문제가 아니라 CB 자체가 이 실행 구조에서 무력**하다. 청산이 실현되기 전에
그날 5건이 이미 다 들어가므로 서킷이 먹일 손실이 없다. → [F-19] 종결, **[F-46] 신설(라이브 전 HIGH)**.

**이건 안전 관련이라 사장님께 정확히 보고드려야 한다**: 7/9 지시서 백테스트에서 "CB 일일 −6%p 유효"로
통과한 것은 **무제한 체결 가정**이었고, 사장님 자금 룰(상한 5건)에서는 아무것도 막지 못한다.
대안 축(택1 이상·**결정은 사장님**): ①미실현 기준 CB ②진입 간격 강제(실현이 CB를 먹일 시간을 만듦) ③건당 손실 상한 하향.

## §4. 판정 숫자 정직성 점검 — "장부가 부당하게 나쁜 것 아닌가"

- 유효일 cap5 51건 중 **SL 청산 23건(45%)** · TP 5 · EOD 23
- SL 청산 실제 ret: 중앙 **−3.52%** · 평균 −3.99% · 최악 −11.35% · **23/23건이 −3%보다 나쁨**
- 해상도 초과손실 합 **−22.66%p**(건당 −0.99%p)

결론: 해상도 편향은 실재하고 크기도 −22.66%p로 작지 않으나, **가장 관대한 가정에서도 판정은 미달**이다.

   - **음성 대조를 안 건너뛰었다.** 정상 케이스만 봤으면 버그 2건(기준일 −1일 오프셋·NameError)을
     그대로 배포했고, 매일 오탐하는 점검기는 첫 주에 신뢰를 잃었을 것이다.
   - **유리한 방향의 반론을 내가 먼저 검정했다**(§4). −69.67이 해상도 탓이라는 변명 여지를
     남기지 않고 −47.01(관대 가정)까지 계산해 부호 불변을 확인했다.
2. **미흡·실수**
   - `last_trading_day`의 시그니처를 **읽지 않고** "직전 거래일이니 today−1을 넣자"고 추측했다.
     정본 docstring에 "d 포함하지 않음"이 명시돼 있었다. VPS가 아니라 **코드를 먼저** 봤어야 했다.
   - 리팩터(main→build_report) 후 **잔여 참조를 grep하지 않고** 컴파일 통과만 믿었다.
     `NameError`는 컴파일로는 안 잡힌다. 리팩터 시 삭제한 지역변수는 전수 grep이 규약이어야 한다.
3. **새 교훈** (영구 메모리 저장 **O**)
   - **"정상 케이스 통과"는 점검 도구의 검수가 아니다.** 감시 도구는 *이상을 만들어 넣었을 때
     빨간불이 켜지는가*로 검수해야 한다. 오늘 두 버그 모두 음성 대조에서만 나왔다.
   - **안전핀은 '검증됐다'가 아니라 '어느 실행 구조에서 검증됐나'로 기억해야 한다.**
     CB −6%p는 무제한 체결 가정에서 유효했고 상한 5건에서는 무효다. 7/30 "전신호 평균=비실행 가정"
