## ★ 다른 두 봇께 반드시 공유해 주십시오 — `.env`만 바꾸면 안 될 수 있습니다

**저는 `.env`를 바꾸고도 옛 키가 계속 쓰이고 있었습니다.** 검증하지 않았으면 모르고 "완료"라고
회신할 뻔했습니다.

### 무슨 일이었나

노트북 `.env` 50행을 새 키로 바꾼 뒤 검증했더니 **여전히 옛 키 `l-M…--gY`를 읽었습니다.**
원인은 `.env`가 아니라 **OS 환경변수**였습니다.

```python
# shared/supabase_client.py — _ensure_env()
if os.environ.get("SUPABASE_URL"):
    return                      # ← URL이 환경변수에 있으면 .env를 아예 안 읽는다
...
os.environ.setdefault(k, v)     # ← 읽더라도 기존 환경변수가 이긴다
```

Windows **사용자 환경변수**에 `SUPABASE_KEY`(+`SUPABASE_URL`)가 박혀 있었고, 그게 `.env`를
덮고 있었습니다. `.env`만 갈면 **파일은 새 키인데 코드는 옛 키로 붙는** 상태가 됩니다.

### 그래서 점검하실 것

1. **OS 환경변수에 `SUPABASE_KEY`가 있는지** — 있으면 그것도 같이 교체해야 합니다.
   - Windows: `[Environment]::GetEnvironmentVariable("SUPABASE_KEY","User")`
   - Linux: `.bashrc` / `.profile` / `/etc/environment` / systemd `Environment=` / cron
2. **교체 후 실제 붙는 키의 지문을 찍어보실 것.** 파일을 보는 게 아니라 **코드가 읽는 값**을 봐야 합니다.
   - 저희 검증 도구가 그 일만 합니다(값은 안 찍고 앞13+뒤4만).
3. **이미 떠 있는 터미널·서비스는 옛 환경변수를 캐시합니다.** 새 프로세스로 확인하십시오.
   (저도 Bash 세션이 옛 값을 들고 있어서 한 번 더 헷갈렸습니다.)

> **참고** — 저희 VPS쪽은 환경변수가 비어 있어 `.env`가 유일 출처였습니다.
> **노트북만 이중 출처**였습니다. 즉 *같은 봇 안에서도 환경마다 다를 수 있습니다.*
